# Physical evaluation evidence capture

**Date:** 2026-11-02  
**Status:** Capture and supervised physical-run integration implemented; physical acceptance pending

`laundrybench.evaluation.capture.EpisodeCapture` records frames from the same
`Observation` objects consumed by a policy. It accepts the evaluator's episode
ID, writes each configured RGB image to an incremental ffmpeg encoder, and on
successful completion writes the existing
`media/<episode_id>/media.json` v1 contract. It does not open cameras, connect
to LeRobot, issue robot actions, or synthesize frames. The caller must start it
for the exact evaluator episode and call `observe` for each observation it
wants captured. On any capture error, the caller must fail the episode/run or
mark its evidence incomplete; it must not report a successful closed loop.

The supervised bridge is wired in `laundrybench.evaluation.physical` through
the callbacks exposed by `run_experiment` and `run_episode`. `on_observation`
starts capture with the exact experiment episode ID and records each fresh
pre-action observation passed to ACT. The configured integer `control_hz` is
also the capture FPS and must match the trained dataset FPS; there is no frame
resampling. `on_episode_complete` finalizes that episode's streams, while any
exception or interrupt aborts capture and propagates the run failure. The
outer physical-run lifecycle stops the robot in its cleanup path. These code
paths implement software behavior; they do not establish hardware readiness
or physical task success.

## Hook contract

The adapter's public lifecycle is:

```python
capture = EpisodeCapture(
    run_root,
    {"front": CameraVideoSpec(width=640, height=480, fps=10)},
    max_clock_error_s=0.1,
)
capture.start(episode_id)               # exact ID used by the evaluator
capture.observe(observation)            # call for each real observation
capture.event("grasp", timestamp_s)     # only for an explicitly recorded marker
manifest = capture.finalize()            # closes encoders, then publishes media.json
```

`abort(reason)` terminates active encoders, removes partial or unregistered
video files, and writes `capture_diagnostics.json`. In the physical evaluator,
`run_episode` calls `on_observation(episode_id, step, observation)` before
`policy.act()` and before action application. `run_experiment` passes that
callback through with `refresh_observation_before_action=True`, so the recorded
frame and the ACT input are the same fresh observation at each policy step.
The terminal post-action observation used only by the pending judge is not
recorded as an extra policy frame. The callback starts each capture with the
`episode_id` generated by `run_experiment` (`<experiment_id>-<index>`), and
`on_episode_complete` finalizes the matching sidecar after the episode record
is written. Capture exceptions propagate out of the rollout; the physical
runner aborts active capture, and the outer `run_physical_experiment` cleanup
stops the robot.

The `on_apply` callback writes `traces/commands.jsonl`, pairing the requested
action with `SO101LeRobotRobot.last_sent_action` (the command after LeRobot's
relative target limit) and both observation and command host timestamps. This
retains requested-versus-sent command provenance without treating the
requested trace as proof of the exact executed motor trajectory.

The generic capture API accepts an FPS no higher than the observed evaluation
cadence. The physical ACT wrapper pins capture FPS to the trained dataset and
runner control FPS; lowering control FPS to run a checkpoint trained at a
higher FPS is unsupported. Each observation contributes one frame. The encoder uses one bounded
raw-RGB pipe per camera and `libx264` MP4 output; it does not keep earlier
frames in memory. Frame arrays must be `uint8` RGB with the configured
`(height, width, 3)` shape. Geometry is explicit and even-sized for
browser-compatible H.264.

## Clock and cadence evidence

`Observation.timestamp_s` is the host wall-clock time sampled after LeRobot
returns the observation. It is not a hardware camera exposure timestamp. The
adapter writes this first timestamp to v1 `trace_start_s`; later clip offsets
are the fixed-rate frame index divided by configured FPS. It checks each
strictly increasing host timestamp against the global affine mapping
`first_timestamp + frame_index / fps`, including cumulative drift, and fails
capture as soon as the configured error budget is exceeded. It does not hold,
duplicate, or synthesize a frame to hide an observation gap. A camera backend
may itself return a stale/repeated image; without a sensor timestamp or frame
counter, the adapter cannot detect that. This establishes a bounded software
observation-to-video clock mapping, not synchronized camera exposure and robot
state.

`capture_diagnostics.json` sits beside `media.json` and records status,
clock-source text, expected FPS, submitted frame count, maximum absolute
timestamp residual, and any failure message. It is provenance, not part of the
v1 media manifest or a physical quality verdict. `media.json` is atomically
published only after every encoder exits successfully and the cadence budget
passes. Encoder writes/finalization have finite deadlines; failure kills and
reaps child processes before returning an error. Per-episode maximum duration
and frame count bound disk use.

Only `finalize()` creates a successful sidecar. Manually named events are
preserved exactly as supplied. No grasp, success, failure, or intervention
event is inferred from pixels, robot state, trace shape, or an outcome. The
media importer remains for explicitly selected existing files; this capture
path records live policy observations instead of attaching unrelated video.

## Validation boundary

Unit tests encode synthetic `Observation` arrays through the real ffmpeg
executable and decode the resulting file. These prove the software path can
encode a supplied RGB sequence and reject invalid cadence, frame shape, capture
limits, and encoder startup failure. They do not prove that a USB camera is
fresh, a LeRobot deployment supplies the expected array layout, an ACT policy
can consume its configured camera keys, or that video is physically
synchronized to motor state. The SO-101 adapter reports host timestamp after
`get_observation`; physical acceptance remains pending on the target host.
The optional LeRobot 0.6.1 CPU ACT integration smoke uses a generated local
checkpoint and synthetic observation arrays. It validates the installed
software package path without camera, robot, GPU, pretrained weights, Hub
access, or a physical acceptance run.
